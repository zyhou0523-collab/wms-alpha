# 出入库订单状态产品决策清单

## 一、背景说明

当前 `release/wms-pc-v2.2` 已完成出入库订单状态字典、状态显示、按钮权限、后端状态校验和历史 demo 数据清洗。现有治理原则已经明确：订单主状态只描述业务进度，SAP 回传结果通过独立字段维护，包装绑定、复核、分配异常和作业任务进度不再污染订单主状态。

本文件不定义新的状态流转，不要求立即开发。它用于沉淀仍需产品、业务和实施侧确认的争议项，便于下一轮确认后再进入设计和开发。

## 二、当前已统一的状态体系

发运订单主状态已统一为：

| 状态 | 名称 | 含义 |
|---|---|---|
| CREATED | 创建 | 发运订单已创建，尚未分配库存 |
| PARTIAL_ALLOCATED | 部分分配 | 部分数量完成库存分配 |
| ALLOCATED | 完全分配 | 全部数量完成库存分配 |
| PARTIAL_PICKED | 部分拣货 | 部分数量完成拣货 |
| PICKED | 完全拣货 | 全部数量完成拣货 |
| PARTIAL_SHIPPED | 部分发运 | 部分数量完成发货确认 |
| SHIPPED | 完全发运 | 全部数量完成发货确认 |
| CLOSED | 订单关闭 | 发运订单完成业务关闭 |
| CANCELED | 订单取消 | 发运订单取消 |

预期到货通知单主状态已统一为：

| 状态 | 名称 | 含义 |
|---|---|---|
| CREATED | 创建 | 预期到货通知单已创建，尚未收货 |
| PARTIAL_RECEIVED | 部分收货 | 部分数量完成收货 |
| RECEIVED | 完全收货 | 全部数量完成收货 |
| CLOSED | 订单关闭 | 当前保留字典和兼容展示，是否形成正式流程待确认 |
| CANCELED | 订单取消 | 入库单据取消 |

SAP 回传状态已统一为：

| 状态 | 名称 | 含义 |
|---|---|---|
| NOT_POSTED | 未回传 | 尚未向 SAP 回传 |
| SUCCESS | 回传成功 | SAP 回传成功 |
| FAILED | 回传失败 | SAP 回传失败 |
| POSTED | 已回传 | 历史兼容值，建议迁移为 SUCCESS |

## 三、仍需产品确认的问题

| 编号 | 问题 | 当前现状 | 方案 A | 方案 B | 推荐方案 | 影响范围 | 是否建议立即开发 |
|---|---|---|---|---|---|---|---|
| 1 | 预期到货通知单是否需要“关闭”流程 | 字典保留 `CLOSED`，页面和主流程尚未形成正式关闭动作 | 保留 `CLOSED` 仅作兼容，不新增关闭按钮 | 建立入库关闭流程，收货完成或上架完成后允许关闭 | 先采用方案 A，待业务确认关闭触发条件、SAP 关系和取消限制后再开发 | 入库列表、详情、按钮权限、后端校验、报表统计 | 否 |
| 2 | 入库 `BOUND` 是否应该作为订单主状态 | 当前 `BOUND` 用于包装/箱托绑定兼容展示，不作为推荐主状态 | `BOUND` 继续作为订单主状态 | `BOUND` 拆为包装绑定状态或作业状态，不进入订单主状态 | 方案 B。包装绑定是作业过程，不应污染订单主状态 | 入库详情、SN 绑定、包装绑定、上架、状态筛选 | 否 |
| 3 | 入库“待收货”是否应该作为订单状态，还是只作为待办标签 | `CREATED` 已统一显示为“创建”，不再显示为“待收货” | 新增 `WAIT_RECEIVE` 或类似订单主状态 | 保持 `CREATED`，页面用待办标签、提醒或筛选表达“待收货” | 方案 B。待收货是用户视角提示，不是独立业务进度 | 入库列表文案、工作台待办、筛选条件 | 否 |
| 4 | 入库 SAP 回传到底按订单展示，还是按收货批次展示 | 当前订单有 `sap_post_status` 汇总，收货批次也有 SAP 状态 | 只按订单展示一个 SAP 状态 | 以收货批次为真实回传粒度，订单展示汇总状态 | 方案 B。SAP 入库过账通常与收货批次/物料凭证相关，订单层做汇总 | 入库列表、收货批次、SAP 重传、接口日志、异常处理 | 是，建议下一轮优先明确 |
| 5 | 发运订单 `REVIEWING / REVIEWED` 是否继续保留 | 已标记为历史兼容状态，现主流程用拣货/发运状态表达进度 | 继续作为订单主状态保留复核阶段 | 拆为复核任务或复核记录状态，订单主状态不使用 | 方案 B。复核是作业任务状态，订单主状态保持简洁 | 出库详情、复核记录、按钮权限、历史数据展示 | 否 |
| 6 | 发运订单 `PENDING_ALLOC` 是否需要保留，还是统一为 `CREATED` | 已作为兼容状态保留，新 demo 和新建订单使用 `CREATED` | 继续保留 `PENDING_ALLOC` 作为主流程状态 | 统一使用 `CREATED`，用按钮和待办表达“待分配” | 方案 B。待分配是创建后的待办视角，不必独立成主状态 | 发运列表、库存分配入口、工作台待办、历史兼容 | 否 |
| 7 | 分配失败是否只做错误提示和操作日志，不进入订单主状态 | 已不推荐 `ALLOCATION_EXCEPTION` 作为主状态，失败写异常/日志 | 分配失败进入订单主状态 | 保持订单原业务进度，失败原因写异常、操作日志或分配结果 | 方案 B。失败不是业务进度，不应破坏订单状态流 | 分配接口、异常中心、操作日志、按钮显示 | 否 |
| 8 | 出库 SAP 回传是否只允许订单关闭后触发 | 当前规则倾向于 `CLOSED` 且 SAP 未成功/失败时允许回传 | 订单 `SHIPPED` 后即可回传 SAP | 订单 `CLOSED` 后才允许回传 SAP | 方案 B。关闭可作为业务确认边界，降低未完成订单误回传风险 | 发运关闭、SAP 回传按钮、后端校验、接口日志 | 否，除非业务要求发货即过账 |
| 9 | 订单状态和作业任务状态是否需要拆分 | 已初步拆分，仍有拣货任务、包装绑定、复核等兼容状态 | 继续混用订单状态表达作业细节 | 明确拆分订单主状态、任务状态、SN 状态、包装状态 | 方案 B。企业级 WMS 应分层管理状态，避免状态爆炸 | 全模块状态模型、详情页展示、报表、权限规则 | 是，建议作为中期治理项 |
| 10 | 订单状态和接口状态是否需要彻底分离 | 已将 SAP 成功/失败迁移到 `sap_post_status`，仍需确认所有接口状态展示口径 | 部分接口结果继续复用订单主状态 | 订单主状态只描述业务进度，接口状态统一独立字段或接口日志 | 方案 B。接口状态应与业务状态彻底分离 | SAP、MES、履约、追溯接口、状态字典、异常处理 | 是，建议下一轮细化 |

## 四、每个问题的现状

1. 入库关闭流程目前只有状态兼容，没有稳定的关闭动作、关闭条件和撤销规则。
2. `BOUND` 来源于包装绑定或箱托绑定场景，更接近包装状态，不是收货订单的主进度。
3. “待收货”是 CREATED 状态下的待办语义，直接做成主状态会与“创建”重复。
4. 入库 SAP 回传既可能从订单层汇总，也可能从收货批次层重传，需要产品确认展示主口径。
5. 出库复核状态来自历史流程，当前主流程可通过拣货完成和发货前校验表达。
6. `PENDING_ALLOC` 与 `CREATED` 在发运主流程初期高度重叠。
7. 分配失败属于操作结果或异常结果，不代表订单进入了新的业务阶段。
8. 出库 SAP 回传触发时机与业务确认边界、财务过账风险相关，需要保持谨慎。
9. 订单、任务、SN、包装、接口都存在状态，后续应形成分层状态模型。
10. 接口状态如果混入订单主状态，会导致列表筛选、按钮权限和报表口径复杂化。

## 五、可选方案

| 方向 | 说明 | 优点 | 风险 |
|---|---|---|---|
| 保守兼容 | 保留当前主状态体系，仅在文档中标记争议项 | 演示稳定，改动小 | 部分业务口径仍需人工解释 |
| 产品确认后收敛 | 先确认争议项，再按优先级逐步开发 | 方向清晰，风险可控 | 需要产品、业务、实施共同评审 |
| 一次性重构状态模型 | 统一拆分订单、任务、接口、包装状态 | 架构最干净 | 风险高，影响面大，不适合当前演示阶段 |

## 六、推荐方案

推荐采用“产品确认后收敛”的方式：

1. 当前演示环境继续使用已治理的主状态体系。
2. 历史兼容状态继续保留显示和筛选能力，但不作为新流程推荐状态。
3. 入库 SAP 回传粒度、入库关闭流程、状态分层模型列为下一轮产品确认重点。
4. 不因页面待办提示新增订单主状态。
5. 不把失败、接口结果、复核、包装绑定直接写入订单主状态。

## 七、影响范围

| 确认项 | 主要影响模块 |
|---|---|
| 入库关闭流程 | 入库列表、详情、按钮权限、后端校验、报表 |
| BOUND 定位 | SN 绑定、包装绑定、上架、入库详情 |
| 待收货口径 | 工作台、入库列表、待办提醒、筛选条件 |
| 入库 SAP 展示粒度 | 收货批次、接口日志、SAP 重传、异常处理 |
| 出库复核状态 | 发运详情、拣货/复核记录、发货校验 |
| PENDING_ALLOC 收敛 | 发运列表、分配入口、工作台待办 |
| 分配失败处理 | 分配接口、异常中心、操作日志 |
| 出库 SAP 触发时机 | 订单关闭、SAP 回传、财务过账风险 |
| 状态分层模型 | 入库、出库、库存、报表、权限、接口 |
| 接口状态分离 | SAP、MES、履约、追溯、接口中心 |

## 八、是否建议立即开发

不建议本轮立即开发。当前阶段应先完成产品确认，避免在状态含义尚未完全定稿时继续扩展流程。

建议立即进入产品评审的问题：

1. 入库 SAP 回传展示口径：按订单汇总还是按收货批次展示。
2. 订单状态、作业任务状态、接口状态的长期分层模型。
3. 入库是否需要正式关闭流程，以及关闭后的可操作范围。

## 九、下一轮开发建议

下一轮建议按以下顺序推进：

1. 产品评审并冻结入库 SAP 回传展示口径。
2. 输出状态分层模型：订单主状态、作业任务状态、SN 状态、包装绑定状态、接口状态。
3. 如确认需要入库关闭流程，再补充关闭按钮、后端校验、关闭日志和关闭后权限矩阵。
4. 将“待收货”“待分配”“待回传 SAP”统一设计为待办标签或工作台任务，不新增订单主状态。
5. 逐步把历史兼容状态从新增流程中完全隔离，只用于旧数据展示和查询。
